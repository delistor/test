什么是上下文窗口

模型的一次"思考"只有这么大

大语言模型没有"脑子"——它每次生成回复时，能看到的全部信息就是发给它的那段文本， 这段文本的容量上限叫上下文窗口（context window），单位是 token。 token 可以粗略理解为"半个到一个词"：中文大约 1 个字 ≈ 1~2 个 token。

窗口里装的是什么

system prompt→长期记忆→对话历史→工具输出→当前问题

这五样东西在抢同一个窗口。工具输出（比如一次 grep 的结果、一张图片的 base64） 动辄上万 token，是最贪心的房客。

关键认知：窗口装不下的内容，模型就完全不知道——不是"记得模糊"，是彻底消失。 第 3 轮说的话，到第 50 轮如果被截掉了，模型等于从没听过。

本报告的主线问题

agent 的记忆系统，本质上就是在回答两个问题： 什么东西值得留下来（写入侧），以及当前这一步该把什么放进窗口（读取侧）。 外加一个救急手段：窗口快满了怎么办（压缩）。后面所有章节都是围绕这三件事展开的。

记忆的三种形态

形态一：窗口内的一切（短期）

最朴素的"记忆"就是消息列表 messages[]。只要还在列表里，模型就记得；被挤出去就忘。 NaiveAgent（第 5 章）就停留在这一形态。

形态二：压缩后的会话摘要（会话内）

当列表太长，把旧消息交给一个（通常更便宜的）模型写成一段摘要，用摘要替换原文。 信息有损，但保住了主线。Claude Code 的 autoCompact、OpenClaw 的 compaction 都是这一形态。

形态三：跨会话的长期记忆

这次对话里学到的事实，下次开新会话还在。存储载体各家不同： markdown 文件（Claude Code / Hermes）或数据库（OpenClaw / mem0 类服务）。

三种形态的关系

对话原文（短期）→摘出事实（写入）→长期记忆库→按任务检索（读取）→注入新会话 prompt

什么是压缩（compaction）

窗口快满时的救急手术

压缩（也叫 compaction / summarization / 摘要）指：当上下文接近窗口上限时， 把较早的消息替换成一段摘要，腾出空间继续对话。

压缩的三个决策点

  1. 什么时候压？——阈值。例如 Claude Code 在"有效窗口 - 已用 token"只剩预留输出空间时触发 （src/services/compact/autoCompact.ts）。
  2. 从哪里切？——切点。不能把正在讨论的话题拦腰截断，OpenClaw 专门有 findCutPoint()（compaction.ts:454）寻找安全切点。
  3. 摘要保留什么？——策略。主流做法是用一个结构化 prompt 让模型摘要：用户目标、 已完成的步骤、关键决定、未完成事项、踩过的坑。

最划算的压缩：先清工具输出

窗口里最占地方、时效最短的往往是工具结果——第 3 轮读的文件内容，到第 20 轮多半没用了。 Claude Code 的 microcompact（microCompact.ts）就是只把旧工具输出 替换成一行占位符 [Old tool result content cleared]，其他消息不动。 这是性价比最高的一刀。

初学者第一条实用经验：做 agent 先实现"清旧工具输出"，十行代码，解决一半的窗口爆炸。

什么是检索召回

记忆库大了，就不能全带

长期记忆只有十几条时，全量塞进 system prompt 没问题。但记忆涨到几百条后， 全量注入既浪费 token 又稀释模型注意力——于是需要检索召回： 按当前任务，只挑相关的几条。

检索的两条技术路线

路线原理优点缺点
关键词/全文检索(FTS)词面匹配（如 SQLite FTS5）零依赖、可解释同义表达匹配不上
向量检索文本→向量，算余弦相似度能匹配语义近似的表达要嵌入模型、结果难解释

生产级实现往往混合检索（hybrid）：两路各打一个分，加权融合。 OpenClaw 的 hybrid.ts、以及本报告配套代码里的 0.6×FTS + 0.4×向量 都是这个思路。

比检索更重要的一步：相关性门控

检索排序解决"哪条最相关"，但没解决"要不要注入"。OpenClaw 的召回代理 （extensions/active-memory/prompt.ts）会先让小模型判断：这次任务有没有必要带记忆？ 没有就明确返回 NONE——塞进噪音记忆比不给记忆更伤。

配套代码里的 overlap_score() 用"中文单字+两字滑窗分词 + Jaccard 重合度" 模拟向量检索的思想。它分不高，但完整演示了"打分→阈值→排序→截断"的骨架。

记忆的生命周期

一个记忆条目的一生

产生→提取→写入(带门槛)→存储→检索→注入→更新/淘汰(策展)
  1. 产生：对话中出现了值得记的信息（用户偏好、项目事实、踩坑经验）。
  2. 提取：谁来发现它？三种模式——模型自己主动写（调记忆工具）、后台评审自动提取 （Hermes 的 background_review）、hook 无差别捕获（OpenClaw 的 session-memory）。
  3. 写入门槛：去重（已存在的拒写）、限容（超上限丢最旧）、冲突处理（新事实覆盖旧事实）。
  4. 策展（curation）：定期整理记忆库——合并同类、归档过期、修剪冗余（Hermes 的 curator.py）。

写入端比读取端更容易烂掉

实践中的最大教训：没有门槛的记忆库会退化成垃圾场。重复条目、过时事实、 无关闲话越堆越多，检索质量随之崩塌。写入端必须有"门"，读取端必须有"闸"。

第 1-5 章会反复回到这张生命周期图，每家 agent 的差异都可以表述为： "它在哪些环节做了什么、没做哪些环节"。

token 经济学：为什么每个 token 都贵

三个成本维度

  1. 钱：API 按 token 计费，输入和输出分别计价。一次注入 5000 token 的记忆， 每次调用都在为它付费。
  2. 注意力：上下文越长，模型对每条信息的"关注密度"越低，指令遵循和检索准确率都会下降。 长上下文不是免费的容量，是稀释的注意力。
  3. 延迟：输入 token 直接拉长首字延迟。

1.1 存储：MEMORY.md 入口文件

入口文件：记忆系统的"首页"

源码 src/memdir/memdir.ts 定义了入口文件常量：

ENTRYPOINT_NAME        = 'MEMORY.md'
MAX_ENTRYPOINT_LINES   = 200      // 最多 200 行
MAX_ENTRYPOINT_BYTES   = 25000    // 最多 25 KB

这两个上限是整个设计的支点：因为入口文件必然全量注入 system prompt， 所以必须从物理上限制它的体积。200 行能写什么？只能放最浓缩的事实：

  • 用户是谁、在做什么项目；
  • 强偏好（"报告必须用表格、注明单位"）；
  • 关键参数（"P99 阈值 320 ms"）；
  • 最近的重要决定。

超限怎么办：truncateEntrypointContent

memdir.ts · buildMemoryPrompt / truncateEntrypointContent

注入前会截断：保住前 200 行 / 25KB，其余丢弃。截断而不是报错——记忆系统必须永远假设 "文件可能被用户或模型写爆"，任何环节都要能优雅降级。

为什么用 markdown 而不是 JSON/数据库？因为记忆的生产者和消费者都是模型， markdown 是模型读写最自然的格式；同时人类可直接审阅——记忆系统的可审计性在生产中极其重要。

真实源码（带注释）：入口文件常量与两级截断

claude-code-src/src/memdir/memdir.ts:34-39 · truncateEntrypointContent（:57-103，节选，注释为讲解）

export const ENTRYPOINT_NAME = 'MEMORY.md'
export const MAX_ENTRYPOINT_LINES = 200
// ~125 chars/line at 200 lines. At p97 today; catches long-line indexes that
// slip past the line cap (p100 observed: 197KB under 200 lines).
// ↑ 源码注释原话：只限行数不够——真实用户写出过"200 行以内却 197KB"的索引
export const MAX_ENTRYPOINT_BYTES = 25_000

export function truncateEntrypointContent(raw: string): EntrypointTruncation {
  const trimmed = raw.trim()
  const contentLines = trimmed.split('\n')
  // 行数、字节数两个维度各自判断是否超限
  const wasLineTruncated = contentLines.length > MAX_ENTRYPOINT_LINES
  const wasByteTruncated = trimmed.length > MAX_ENTRYPOINT_BYTES
  if (!wasLineTruncated && !wasByteTruncated)
    return { content: trimmed, lineCount, byteCount, wasLineTruncated, wasByteTruncated }
  // 第一级：按行截断
  let truncated = wasLineTruncated
    ? contentLines.slice(0, MAX_ENTRYPOINT_LINES).join('\n')
    : trimmed
  // 第二级：按字节截断。cutAt 取换行符位置——宁可少留一行，
  // 也不把一行从中间劈开（半行会被模型当成完整条目理解）
  if (truncated.length > MAX_ENTRYPOINT_BYTES) {
    const cutAt = truncated.lastIndexOf('\n', MAX_ENTRYPOINT_BYTES)
    truncated = truncated.slice(0, cutAt > 0 ? cutAt : MAX_ENTRYPOINT_BYTES)
  }
  // 截断不是悄悄进行的：在注入内容末尾追加 WARNING，
  // 让模型知道"索引只加载了一部分，长条目应移入主题文件"
  return { content: truncated + `\n\n> WARNING: ${ENTRYPOINT_NAME} is ${reason}...`,
           lineCount, byteCount, wasLineTruncated, wasByteTruncated }
}
读源码的两个收获：① 字节截断回退到最近的换行符，绝不劈开条目；② 截断后注入一段 WARNING——降级必须让消费方（模型）知情，而不是静默丢数据。

def scan_manifest(self):
    out = []
    for fn in os.listdir(self.root):
        if fn == "MEMORY.md" or not fn.endswith(".md"):
            continue
        head = open(os.path.join(self.root, fn), encoding="utf-8").read(400)
        m = re.search(r"description:\s*(.+)", head)
        out.append((fn, m.group(1) if m else fn))
    return out   # [(文件名, 描述), ...] —— 与 memoryScan.ts 同构

const MAX_MEMORY_FILES = 200        // 清单最多 200 个文件
const FRONTMATTER_MAX_LINES = 30    // 每个文件只读前 30 行

export async function scanMemoryFiles(memoryDir, signal) {
  const entries = await readdir(memoryDir, { recursive: true })
  const mdFiles = entries.filter(
    f => f.endsWith('.md') && basename(f) !== 'MEMORY.md',  // 入口文件不进清单
  )
  const headerResults = await Promise.allSettled(   // 并发读；单个失败不拖垮整库
    mdFiles.map(async (relativePath) => {
      const { content, mtimeMs } = await readFileInRange(
        filePath, 0, FRONTMATTER_MAX_LINES, ...)   // 只读文件头 30 行
      const { frontmatter } = parseFrontmatter(content, filePath)
      return { filename, filePath, mtimeMs,
               description: frontmatter.description || null, ... }
    }))
  return headerResults.filter(r => r.status === 'fulfilled').map(r => r.value)
    .sort((a, b) => b.mtimeMs - a.mtimeMs)   // 按修改时间 新→旧
    .slice(0, MAX_MEMORY_FILES)                // 硬上限 200 条
}

export function formatMemoryManifest(memories) {  // 清单的真实长相：
  return memories.map(m => {
    const tag = m.type ? `[${m.type}] ` : ''
    const ts = new Date(m.mtimeMs).toISOString()
    return m.description
      ? `- ${tag}${m.filename} (${ts}): ${m.description}`
      : `- ${tag}${m.filename} (${ts})`
  }).join('\n')
}
三个防失控细节：单文件只读 30 行、并发用 allSettled（一个文件损坏不影响整库）、清单截断到 200 条。教学版 scan_manifest() 的"只读前 400 字符"对应这里的 FRONTMATTER_MAX_LINES。

1.3 读取：双轨注入的设计

两条注入轨道

轨道A: MEMORY.md 全量注入(永远在场)→轨道B: memdir 挑选注入(按任务携带)

这是 Claude Code 记忆系统的灵魂设计：重要的少量记忆永远在场，详细的多数记忆按需携带。

维度轨道 A：入口文件轨道 B：记忆目录
体积≤200 行 / 25KB，严格受限理论无上限（由检索控制）
注入时机每次请求，拼入 system prompt检索命中才注入
谁决定注入无人决定——无条件小模型从描述清单中挑选
典型内容身份、强偏好、关键参数详细配置、历史记录、教程性内容

防重复：轨道 B 排除轨道 A

findRelevantMemories 明确排除已在 system prompt 中的入口文件， 避免同一条记忆以两种形式重复占用窗口。听起来简单，但这是很多自研记忆系统会踩的坑： 注入去重必须在"注入层"做，不能指望模型自己忽略重复。

源码位置

算法五步

  1. 取清单：调用 memoryScan 拿到所有 (文件名, description) 对；
  2. 排除入口：MEMORY.md 已在轨道 A，剔除；
  3. 构造挑选请求：把清单 + 当前任务（sideQuery）发给一个小模型（Sonnet）， 系统提示词 SELECT_MEMORIES_SYSTEM_PROMPT 要求它返回与任务相关的文件；
  4. 截断：上限 5 个——注意真实源码里没有独立常量，"up to 5" 直接写在挑选提示词文本里（见下方源码），防止"全都相关"的失控；
  5. 读取全文：只把选中的 5 个文件读出来，注入上下文。

成本账

挑选本身只花"清单 + 任务"的 token（清单 O(条数)，每条只有一句话）。 用几百 token 的挑选成本，换取避免了"全库注入"的几千上万 token——划算。

为什么要分四级

  • ① 的信息损失最小：工具输出本来就该被"结果已被吸收"取代；
  • ② 是主力：真正把几十轮对话滚成摘要；
  • ③ 是保险：② 的阈值估计失手时（比如用户粘贴了超大文件），API 会直接拒绝请求， ③ 兜住这种情况；
  • ④ 是控制权：把决定权还给用户。
    • 压缩体系的通用原则：损失小的先做、损失大的后做、全部失手要有兜底。 这个次序在 OpenClaw 和 Hermes 里同样成立。

microCompact 不是无差别清理，源码维护了一个可压缩工具的白名单：

白名单的含义：这些工具的输出是环境快照——随时可以重新执行获得。 而模型自己的推理、用户的指令不在白名单里，永不被清。

1.4 压缩：autoCompact 阈值设计

什么时候触发：给输出留余量

autoCompact.ts · getEffectiveContextWindowSize()

触发条件不是"用满窗口"，而是：

有效窗口 = 模型窗口 - 预留输出空间(20k token)
触发压缩：已用 token > 有效窗口 - 安全边际

预留 20k 的原因：压缩后模型要生成摘要 + 回复，如果输入把窗口吃满，输出就没有空间了。 这个余量还支持环境变量 CLAUDE_CODE_AUTO_COMPACT_WINDOW 覆盖。

摘要替换什么

  1. 确定保留区间：最近若干轮 + 所有未完成话题相关消息；
  2. 把更早的消息交给模型生成结构化摘要；
  3. 摘要作为一条特殊消息放回，其后接保留的原文；
  4. postCompactCleanup.ts 做压缩后的清理（失效的工具引用等）。

function toDecayLambda(halfLifeDays: number): number {
  if (!Number.isFinite(halfLifeDays) || halfLifeDays <= 0) return 0

  const captured = []; let capturedBytes = 0; let offset = 0
  let totalMessages = Infinity
  while (
    offset < totalMessages &&
    offset < SESSION_MEMORY_CAPTURE_MAX_SCANNED_MESSAGES &&  // 三重围栏：

2.3 读取：混合检索打分

hybrid.ts：两路分数加权

每条候选记忆得到两个分：

  • FTS 分：关键词重合（词面相关）；
  • 向量分：嵌入余弦相似度（语义相关）。

归一后加权融合。配套代码采用 0.6×FTS + 0.4×向量：

def hybrid_search(self, query, top_k=3):
    qv = self._vec(query)
    results = []
    for r in self.rows:
        fts = overlap_score(query, r["text"])
        vec = self._cos(qv, r["vec"])
        results.append((0.6 * fts + 0.4 * vec, r["text"], fts, vec))
    results.sort(reverse=True)
    return results[:top_k]

再加一层：MMR 多样性重排（mmr.ts）

纯按分数排序容易召回 5 条几乎相同的记忆。MMR（Maximal Marginal Relevance）在 "相关性"和"彼此不相似"之间平衡——第 2 条记忆不仅要在意"和查询多相关"， 还要在意"和已选的第 1 条多不同"。

打分只是起点

hybrid 打分→temporal-decay 时间衰减→importance 重要性→project-ranking 项目加权→MMR 去冗余→top-k 截断

这就是数据化记忆库的优势：每一环都是一个可以独立调整的打分器。

2.3 读取：门控阈值的第一手教训

修复前: 无关任务 混合分 0.26 → 注入了无关记忆（错！）
修复后: 要求 FTS 分 > 0（确实聊到同一件事）且混合分 > 0.2

教训抽象成三条

  1. 低质量信号不能单独做判据——假向量/弱模型给的分数只能加权辅助，不能一票通过；
  2. 门控要用"最强证据"做底线——FTS 词面重合是强证据（聊到了同一个词）， 向量分只是弱证据（整体相似）；
  3. 每个阈值都要用正反例测——准备几组"应该注入/不应该注入"的任务做回归测试。
生产级系统里，门控判断交给小模型而不是阈值——小模型能理解 "分析延迟对照基线"和"P99 阈值 320 ms"是相关的（哪怕没有词面重合）。 阈值门控是它的廉价替代，适合同义词少的场景。

为什么一个 markdown 文件需要这么多防御

漏带风险的真实形态

模型看到任务"分析延迟对照基线"时，它怎么知道库里有"P99 阈值 320 ms"这条记忆？ 它不知道——工具列表只说"按查询取相关记忆"。是否调 retrieve 全凭模型判断。 实践中缓解方法：在 system prompt 里写"处理 X 类任务前先查记忆"，或框架在特定时机 自动代查一次塞进上下文（OpenClaw 的 trigger-recall 就是这种"自动代查"的精细化）。

  • 任务多样，预注入大概率浪费；
  • 框架侧工程资源有限——先让记忆"能用"。

流派一：文件派（Claude Code、Hermes 内建）

流派二：数据派（OpenClaw）

6.6 总结论：记忆系统的十个设计原则

从五家源码中提炼

  1. 记忆有三种形态（窗口内/会话摘要/长期库），先想清楚你在建哪种；

  3. 写入要三防：去重（门槛）、限容（上限）、过期（策展）；

  8. 压缩从清工具输出开始：白名单+保留最近 N 条，性价比之王；
  9. 压缩要保全原文：事件化/快照，且必须处理摘要套摘要；
  10. 记忆要有运维面：用户能查看、能改、能一键清空。

class ClaudeCodeMemory:
    MAX_ENTRY_LINES = 6      # memdir.ts: MAX_ENTRYPOINT_LINES=200（教学版缩小）
    RELEVANT_LIMIT = 5       # findRelevantMemories 最多挑 5 个相关文件

    def write_entrypoint(self, lines):
        """入口文件只放最重要的几行（真实版超 200 行会截断）"""
        body = "\n".join(f"- {l}" for l in lines)[: self.MAX_ENTRY_LINES * 80]
        open(self.entrypoint, "w", encoding="utf-8").write(
            "# 自动记忆入口\n" + body + "\n")

    def write_memory_file(self, name, description, content):
        """memdir 目录：每条详细记忆一个文件，frontmatter 存描述"""
        with open(os.path.join(self.root, name), "w", encoding="utf-8") as f:
            f.write(f"---\ndescription: {description}\n---\n{content}\n")

    def scan_manifest(self):
        """memoryScan.ts：只读文件头做清单（不读全文，省 token）"""
        out = []
        for fn in os.listdir(self.root):
            if fn == "MEMORY.md" or not fn.endswith(".md"):
                continue
            head = open(os.path.join(self.root, fn), encoding="utf-8").read(400)
            m = re.search(r"description:\s*(.+)", head)
            out.append((fn, m.group(1) if m else fn))
        return out

    def find_relevant_memories(self, query):
        """真实实现是把 manifest 发给小模型(Sonnet)挑选；
        教学版用词重合打分代替，同样最多返回 5 个。"""
        scored = []
        for fn, desc in self.scan_manifest():
            s = overlap_score(query, desc + " " + fn)
            if s > 0.02:                          # 阈值之下视为无关
                scored.append((s, fn, desc))
        scored.sort(reverse=True)
        return [(fn, desc) for _, fn, desc in scored[: self.RELEVANT_LIMIT]]

    def build_system_prompt(self, query):
        """双轨注入：入口文件全文 + 相关文件的【描述】"""
        entry = "\n".join(open(self.entrypoint, encoding="utf-8")
                          .read().strip().splitlines()[1:])
        p = ("你是编程助手 Claude Code。\n\n# 自动记忆（长期）\n" + entry + "\n")
        relevant = self.find_relevant_memories(query)
        if relevant:
            p += "\n## 与当前任务相关的记忆文件\n"
            for fn, desc in relevant:
                p += f"- {fn}: {desc}\n"
        return p

    def hybrid_search(self, query, top_k=3):
        """hybrid.ts：FTS 分(词重合)与向量分(余弦)加权融合"""
        qv = self._vec(query)
        results = []
        for r in self.rows:
            fts = overlap_score(query, r["text"])
            vec = self._cos(qv, r["vec"])
            results.append((0.6 * fts + 0.4 * vec, r["text"], fts, vec))
        results.sort(reverse=True)
        return results[:top_k]

    def recall_agent(self, query):
        """召回代理门控：FTS 必须 >0（强证据），假向量只作辅助——
        它噪声大，不能单独当判据"""
        hits = self.hybrid_search(query)
        if not hits:
            return None, "NONE"
        combined, text, fts, vec = hits[0]
        if fts <= 0.0 or combined < 0.2:
            return None, "NONE"
        return hits, "INJECT"

    def add(self, kind, text):

            return "SKIPPED_DUPLICATE"      # 不报错，让调用方可感知
        _, fn, cap = self.files[kind]

class DshMcpMemoryServer:
    """模拟一个外部 MCP memory server（如 Memorix / Engram）"""
    def store_memory(self, text):
        self.store.append(text)
        return f"stored #{len(self.store)}"       # server 侧只认序号

def tokens(text):

    cjk = re.findall(r"[\u4e00-\u9fff]", text)             # 中文字
    bigrams = [text[i:i+2] for i in ...]                    # 中文2字滑窗
    return [w for w in words + cjk + bigrams if w not in _STOP]

中文没有空格分词。教学版用"单字 + 2 字滑窗"：基线阈值 → {基线, 线阈, 阈值, 基, 线, 阈, 值}。两字滑窗能抓住大部分中文词， 代价是产生噪音二元组——Jaccard 打分下噪音被稀释，够用。

overlap_score()：Jaccard 重合度

def overlap_score(query, text):
    q, t = set(tokens(query)), set(tokens(text))
    if not q or not t: return 0.0
    return len(q & t) / len(q | t)     # 交集/并集

TF-IDF 余弦考虑词频与稀有度条目变长时
BM25检索界金标准条目上百时
